# StreamLink — a shared One Health record for every urban stream

**OneAquaHealth IEEE Global Hackathon 2026 · Track 7: Digital Health Standards**

Maps give each stream a history. Volunteers report what maps and rare lab visits miss. The lab confirms. Everything lands in one living record, in the standard the OneAquaHealth project already uses.

> Each of the 96 OneAquaHealth lab sites has **one** lab health-risk campaign on record, and 95 of them are from **2023**. StreamLink keeps that picture current between lab visits, and tells the city where to send the lab next.

## The record lifecycle

| Step | What happens | In FHIR |
|---|---|---|
| **1. Check-in** | A volunteer does a 3-minute, picture-based stream check, field for field the same as the OneAquaHealth Citizen Science App (its published field protocols: doi.org/10.5281/zenodo.20344421). Works offline: the app is installable and queues checks with no signal. | `QuestionnaireResponse` + `Observation` (status `preliminary`) + pseudonymous `Practitioner` |
| **2. Trust** | Plain-language consistency checks ("you rated it good but reported sewage"). The volunteer fixes or confirms. | `Provenance` with a `sl-trust-assessment` extension (score + flags + how each was resolved) |
| **3. Verification** | An expert confirms the check. Observations become `final` and then **also conform to the official OAH indicator profile**. | `Provenance` (verifier) + `meta.profile` gains `observation-indicators-oah` |
| **4. Referral** | The city ranks streams by fresh reports × trust, last lab result, map context and data age, then requests a lab visit. The request carries its reasons. | `ServiceRequest` with `reasonReference` to the volunteer's observations |
| **5. Result** | The lab result closes the request and settles the reports that triggered it. | `Observation.basedOn` → the request |
| **6. Feedback** | The volunteer is told their report led to a lab visit. | `Communication` |
| **7. Anywhere** | A new city is added from a config file: map features come from OpenStreetMap, so cities with no lab data still get a baseline. | `Location` + baseline `Observation` |

## Why this is not just "uses FHIR"

- The official OneAquaHealth IG has **no model for citizen checks**, and its indicator profile requires `status = final`, so an unverified volunteer report cannot conform to it. StreamLink adds a **proposed extension** (`fhir/`): a Questionnaire mirroring the app, 9 profiles, 2 extensions, code systems, value sets and a ConceptMap onto OAH indicator codes, with the citizen→verified promotion built in.
- Every record type the app writes is checked by the **official HL7 validator** against the OAH IG plus ours, and deliberately broken records are checked to fail.
- The record is portable: it uses only standard FHIR R4 REST (transactions with conditional creates, search), so it is not tied to one server. It ships with an in-browser demo store and can be pointed at the official OneAquaHealth sandbox (verified by reading from it; writing to that shared server is off by default).

## Run it

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # unit + lifecycle tests
npm run build      # static bundle in dist/
npm run e2e        # end-to-end walkthrough in a real browser (needs npm run dev)
npm run validate   # regenerate fixtures, run the HL7 validator, publish the summary
```

`npm run validate` needs Java; `scripts/validate.sh` will point you at a portable JRE and the validator jar if they are missing (both land in the gitignored `tools/`).

## Architecture

```
Browser (static SPA, no backend of ours)
 ├── src/core   engine: questions → FHIR, trust rules, triage, record assembly, lifecycle
 │              (pure TypeScript, reusable as a library by the OAH app itself)
 ├── src/app    three views: city board · stream check · stream record
 └── FhirStore  ─┬─ LocalStore   in-browser demo store (offline, nothing leaves the device)
                 └─ RemoteStore  any FHIR R4 server (e.g. the OneAquaHealth sandbox)
fhir/       the proposed IG extension (FSH → SUSHI), with examples and negative tests
analysis/   OpenStreetMap features + the calibrated map-context baseline
data/       OneAquaHealth snapshots, baseline outputs, city configs
```

The FHIR server **is** the backend: there is no database of ours, no account system and no server to run. Hosting is a static file host; operating cost is effectively zero.

## Privacy

Volunteers are pseudonymous: a random code, with no name, e-mail or device identifier in any FHIR resource. The submitted position is rounded to about 100 m in the stored record (a pseudonym plus an exact place and time can identify a person); the precise position is used only on the device, to check you are at the site. Photos stay on the device in this prototype. Wellbeing answers are attached to the stream, not to a person, and are labelled self-reported rather than clinical.

## Honesty

- **Real:** the OneAquaHealth site list and lab health-risk scores (Resilience Map snapshot, © OneAquaHealth), the map features, the FHIR resources and their validation, and the whole workflow.
- **Synthetic and labelled:** the demo scenario's volunteer checks, and every lab *result* recorded in the app (tagged `simulated` in FHIR).
- **Not claimed:** that the trust rules or the map baseline predict contamination beyond the evaluation in `analysis/REPORT.md`. Volunteers are positioned as event reporters, not as a substitute for lab work.
- **No biological indicator** (macroinvertebrates, diatoms), because the OneAquaHealth citizen form has none: it collects habitat, water appearance, banks and an overall rating (field protocols: doi.org/10.5281/zenodo.20344421). Those indicators come from the professional protocol and the lab, which is exactly what a referral asks for.
